# 校准整理

整理不是每天分析用户。

只是隔一段时间回头看一眼：哪些更准了，哪些该删，哪些还不能说死。

校准处理的是单点：某条画像被纠错、被确认、被质疑时，当场修那一条。批量的沉淀和修剪走深度整理（`dream.md`），别在校准里顺手做全量重写。

## 什么时候校准

可以校准：

- 用户明确确认。
- 用户明确纠错。
- 同一类问题反复不准。
- 某条画像已经影响回答质量。
- 用户主动要求复盘。
- 校准时发现行为模式与画像矛盾。

不要校准：

- 用户已暂停或删除画像。
- 只是闲聊。
- 用户正在赶任务。
- 只是为了让画像看起来完整。

## 怎么判断有没有用

只问一句：

```text
这份画像，下次真的能帮回答更合适吗？
```

证据强弱大致这样看：

```text
用户纠错 > 用户确认 > 多轮真实任务反复出现 > 用户盲选 > 用户自述 > 第三方评价 > 自己推测
```

盲选指用户在不知道哪个"符合画像"的情况下，自然选中了某种回答方式——比标签化的自述更可信，因为没有迎合成分。

只靠推测，别把把握抬高。

如果用户自述和行为打架，回答先按行为走，把矛盾留在"还待确认"。

## 用户主动要求复盘

先列提案，再动手：打算改什么、删什么、为什么，摆给用户看，确认后才改。拿不准归哪类的条目直接问，不要猜。

## 校准时发现行为-画像矛盾

校准时发现行为模式与画像记录矛盾（如画像记"偏好简洁"，但近期3次以上要求展开）：

- 不应单方面删除原有判断——可能存在场景差异。
- 可降低把握度，或标注矛盾点。
- 下次交互时自然确认，不主动追问"你之前说喜欢简洁"。
- 如果有明确场景规律，按场景拆分。

## 状态

内部状态用"低 / 中 / 高"就够。

```text
当前理解：中
比较稳：接受结论前会先看来源。
还不稳：正式场合下要多完整。
最近改动：把"喜欢短回答"改成"不怕展开，但要有依据"。
```

没有明确要求数字时，不要主动给分。"可用性""分项"也用低 / 中 / 高。

用户或外部界面明确要一个数字时，可以给 0-100，但它只是展示口径，不是"了解用户百分比"，也不是科学量表。

用户纠错或盲选说明它不准，就改。

## 定时回看

周期性整理的触发和流程统一走 `SKILL.md` 的"整理的必然触发"和 `dream.md`，不在这里另设一套时间表。

写入门槛不按条数算。只看它是否被确认、被纠错、在真实任务里反复出现，并且会改变以后怎么回答。

## 整理时怎么留

整理记录可以很短：

```text
看过：最近几段相关对话。
写入：不怕展开，但要有依据。
没写：正式交付要多完整，还待确认。
下次留意：用户赶时间时是否仍要依据。
```

聊得越多，越要先删后写。只留下下次回答真的用得上的东西。

画像长期很薄的处理见 `form-profile.md` 的"持续低可用性"——校准时同样适用：薄不是问题，不要为了让画像显得完整而主动试探。
